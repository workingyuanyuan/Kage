# 內容策略

這份文件管內容：寫什麼、寫到什麼程度、什麼時候不該寫。版面與材質見 `design.md` 與 `material.md`，不該做的事見 `anti-patterns.md`，每種類型的欄位與長度上限見 `schemas/`。

## 兩種語氣模式

同一份材料可以用兩種語氣寫出來。模式決定**用詞與句法**，不決定內容的真假、結構或品質門檻 —— 後三者兩個模式共用，沒有例外。

| | 標準模式（預設） | 顯影模式（可選） |
|---|---|---|
| 適用 | 對外文件、投資人材料、技術文件、變更紀錄 | 作品集、封面、章節扉頁、品牌敘事 |
| 語域 | 專業、直述、可被引用 | 客觀觀察者視角，冷澈的實體紀錄 |
| 判準 | 讀者能否據此做決定 | 讀者能否據此做決定（**不變**） |

**預設是標準模式。** 顯影模式必須由使用者明確指定才啟用 —— 它是一層可選的語氣，不是這個 skill 的預設人格，實務上絕大多數文件都不會用到。使用者沒說，就用標準模式。

**不隨模式改變的東西**（切到顯影模式不構成放寬任何一條）：

- 所有數字仍須可追溯，來源仍須可查。
- 各類型的品質門檻與內容契約（`references/schemas/`）完全相同。
- `references/anti-patterns.md` 全部條目照常適用。
- 一份文件只用一種模式。不要在同一份文件裡混用，那讀起來是兩個人寫的。

**混合的唯一情況**：A 級敘事型頁面（封面、章節扉頁、標題投影片）可用顯影模式，同一份文件的 B／C 級內頁仍走標準模式。這對應版面分級 —— 敘事型畫面本來就承擔氣氛，內頁承擔資訊。

## 核心原則

本節定義所有 HTML 文件類型通用的寫作原則。好的排印搭配空洞內容僅是「精美的平庸」，內容策略必須優先於版面編排。

### 1. 數據高於形容詞

避免使用「顯著成長」、「大幅提升」、「廣大用戶」等模糊形容詞。任何主張都必須承受「具體是多少？」的追問。寫作時必須給出基準值、最終數值與變動幅度（如：「營收年增 34% 達 1,200 萬美元」、「p99 延遲從 800ms 降至 120ms，每年節省 34 萬美元成本」）。若無法給出精確數字，應誠實寫出數量級範圍，而非填充抽象形容詞。

### 2. 判斷高於執行

初級寫作記錄「做了什麼」，中級寫作描述「怎麼做的」，高級寫作則聚焦於**「為何做此決策、進行了哪些權衡取捨，以及當初正確預測了什麼」**。避免平淡的工作清單，改為寫出決策背後的判斷邏輯（如：「選擇事件溯源架構，預先解決跨區域同步的最終一致性衝突」）。

### 3. 獨特表達高於產業套話

嚴禁使用企業套話與 AI 贅詞，如：「賦能企業數位轉型」、「打造一站式解決方案」、「發揮優勢以釋放綜效」、「擁抱 AI 時代新範式」、「重構商業底層邏輯」。獨特表達才能建立專業識別。文案應來自真實思考與具體實務，能用平實日常專業語言說明的事，絕不套用抽象概念名詞。

### 4. 誠實邊界

- 未親自完成的事項絕不誇大為獨占成果，明確標註合作者與團隊範疇。
- 無權威來源時，嚴禁捏造帶假小數點的數據（如未實測寫出「市占率 23.7%」），改用誠實數量級（如「約 24%」）。
- 主動說明方案適用條件與限制邊界，這比單方面宣稱完美更具可信度。

### 5. 來源先於文案

針對公司名稱、產品功能、發布日期、版本號碼、融資與財務數據、市場市占率或技術規格，撰寫前必須先向權威來源核實。
核實順序：使用者提供之原始材料 > 官方網站 / 文件 / 新聞稿 > 監管申報 / 商店 / Repo Release > 具公信力主流媒體。

- 未核實前嚴禁寫出「最新版」、「最新推出」或具體版本號。
- 來源衝突時標記並向使用者確認，不得隨機挑選；僅掌握大致數量級時寫數量級即可，不捏造假精確數字。

### 6. 材料服務於識別

文件與頁面應先確保受眾能清晰識別標的物，再克制地使用材質與裝飾。寫作與版面規劃前，必須先確認以下三類實體材料：

1. **品牌標誌 (Logo)**：矢量標誌或高解析透明圖檔。
2. **產品圖片 (Product Image)**：實體產品採用官方實拍照。
3. **UI 介面截圖 (UI Screenshot)**：數位軟體採用真實操作介面截圖，不得以概念 Mockup 充數。

**缺口與重繪規範**：
- 核心材料缺失時，版面上必須明確標註「素材缺口標示」，不得使用無關意境圖充數。
- **示意重繪標示**：重繪論文插圖、專利圖或架構圖時，圖說必須明確標註「示意重繪」（Schematic redrawn），不得偽裝成原始截圖；具備主要證據價值的圖表應直接嵌入原圖並標明出處。

### 7. 術語標注半衰期

專業術語與英文縮寫首次出現時提供中文註解。讀者記憶具有半衰期，超出視窗後註解失效需重新標註，但視窗內部不得重複標註。

- **首次出現**：提供完整名稱與動作說明，如 `LTV (Lifetime Value，用戶在流失前貢獻的總收入)`。
- **半衰期視窗與重標規則**：
  - 在長篇報告（`long-doc`）、個股報告（`equity-report`）中，以 **8–10 頁** 為半衰期視窗；在簡報（`slides`）中，以 **10 張投影片** 為半衰期視窗。
  - 當術語超出半衰期視窗再次出現時，採用簡短形式重新標註，如 `LTV (用戶終身價值)`。
  - **視窗內禁止重複標註**：在半衰期視窗內部再次出現時直接使用縮寫 `LTV`，不得頻繁重複解釋。
- **短文件免觸發**：單頁摘要（`one-pager`）、商務書信（`letter`）與更新日誌（`changelog`）篇幅過短，全篇僅在首次出現時標註一次或不標註。

### 8. 中文中的英文術語密度

嚴格控制繁體中文正文內的英文術語數量與翻譯方式：

- **密度上限**：單一繁體中文句子中，未經註解的英文專業術語**不得超過 1 個**。超過時須拆分為複句，或加上行內中文說明。
- **動作詞優先於概念詞**：行內中文翻譯或註解時，**優先使用描述「發生了什麼」的動作詞**，避免僅換一層外殼的抽象概念名詞。
  - 壞例（概念名詞）：`warmup` 譯為「預熱」；`rollout` 譯為「軌跡生成發布」；`credit assignment` 譯為「信用分配」；`graceful degradation` 譯為「優雅降級」。
  - 正例（動作說明）：`warmup` 描述為「將系統或快取升溫預熱」；`rollout` 描述為「全量跑一遍生成與發布」；`credit assignment` 描述為「將貢獻度追溯歸因至具體步驟」；`graceful degradation` 描述為「在資源不足時平滑降級維持基礎運作」。

## 各類型的內容策略

本專案僅涵蓋八種 HTML 文件類型。每種類型皆有其讀者決策目標、篇幅字數上限、開頭結尾結構與常見品質陷阱。

### 1. 單頁摘要 (one-pager)

- **讀者決定**：讓忙碌的高階決策者在 **30 秒內** 抓取提案或產品的核心主張、量化證據與投資回報，決定是否批准下一步或深入審閱。
- **篇幅目標**：繁體中文正文 **400–600 字**（在 1280×800 視窗內一屏可讀完，不需捲動）。
- **開頭與結尾規則**：
  - 開頭：襯線大標題（`display`）+ 單行無襯線副標題（`sans body`），緊接著 3–4 張數據指標卡片（Metrics Cards）。
  - 結尾：頁尾包含單一明確的下一步請求（Ask，如申請試用、簽署意向書）與聯絡方式。
- **最容易寫壞的地方**：加入「在當今瞬息萬變……」等填料開場白；數據未達正文面積 30% 以上；小標題僅寫「背景介紹」等主題標籤而非陳述句。

### 2. 長篇報告與企劃提案 (long-doc)

- **讀者決定**：供團隊或客戶深度評估複雜專案、技術架構、市場研判或商業合作（整合提案 Proposal 變體）的合理性、風險、資源配置與執行時程。
- **篇幅目標**：繁體中文 **2,000–6,000 字**（單章 **800–1,500 字**；執行摘要獨立占一頁，篇幅 **300–500 字**）。
- **開頭與結尾規則**：
  - 開頭：包含獨立「執行摘要」頁面列出 3–5 個核心結論；章節（h2）開頭第一段必須為 2–3 句的「主張段落」（Claim Paragraph）。
  - 結尾：包含完整附錄、數據來源對照表與階段性檢驗點（Milestones）。
- **企劃提案 (Proposal) 併入策略**：
  - **注意力框架 vs 工作量框架**：高階顧問提案採「注意力框架」（賣專家在關鍵方向上的判斷力配置），禁止「工作量框架」（明細化列出工時、文章篇數或會議次數）。禁止出現 `每月 N 篇`、`20 堂課` 或 `全程參與` 等外包字眼。
  - **含價 vs 無價版本**：直接買家採含價版本；中間轉發人／董事會採無價版本（章節名改為「合作方向與價值」）。
  - **啟動期強調寫法 (Story before Grid)**：12 個月時程表前，先以獨立段落強調前 60 天啟動期的時間緊迫性與具體動作，再附完整月份表格。
- **最容易寫壞的地方**：連續超過 5 行大段落未穿插提示框/引用區/圖表；章節第一句無法獨立站立；未保留來源標示區分事實與推論。

### 3. 商務書信 (letter)

- **讀者決定**：傳達具體商務立場、人事決定、推薦意圖或合作邀請，建立具約束力的專業書面紀錄。
- **篇幅目標**：繁體中文 **300–600 字**（3–5 個段落，嚴格限制單頁不捲動）。
- **開頭與結尾規則**：
  - 開頭：第一段在單一句子內點明寫信目的與核心訴求（如：「本信旨在正式提議 2026 年度供應鏈自動化模組整合方案」）。
  - 結尾：最後一段寫出明確請求或下一步約定；署名使用 600 字重襯線體與對應敬語（如「順頌商祺」、「敬禮」）。
- **最容易寫壞的地方**：加入裝飾性卡片框線或漸層；段落過密；採用一般 14px 小字（應採用 16–18px 襯線體）；篇幅溢出至第二頁。

### 4. 更新日誌 (changelog)

- **讀者決定**：讓使用者與開發者在 **10 秒內** 掌握新版本變更對既有系統與操作的具體影響，決定是否立即升級。
- **篇幅目標**：繁體中文單一版本 **400–800 字**（每個版本包含 4–8 個變更條目）。
- **開頭與結尾規則**：
  - 開頭：重大破壞性變更（Breaking Changes）強制置於最頂端並附帶遷移路徑（Migration Path）；條目依 Breaking / Features / Fixes 分組。
  - 結尾：標註發布日期與快照版本號（如 `v2.4.0 · 2026.04`）。
- **最容易寫壞的地方**：使用開發者內部術語（如「重構內部佇列」而非「修正 iPad 切換分頁閃退」）；變更未以動詞開頭；項目少於 4 項即單獨佔頁。

### 5. 作品集案例 (portfolio)

- **讀者決定**：評估創作者或團隊在真實專案中的核心問題解決能力、設計判斷與最終量化影響力。
- **篇幅目標**：繁體中文總篇幅 **1,200–2,500 字**（精選 3–5 個深度案例，單一案例 **300–500 字**）。
- **開頭與結尾規則**：
  - 開頭：每個案例開頭第一句直接說明「問題與代價」（如：「用戶登入後 73% 放棄使用分析儀表板」），禁止以專案名稱或職銜開場。
  - 結尾：達成三層成效閉環：量化指標（如「放棄率降至 31%」）+ 定性用戶引言 + 商業脈絡（如「ARR 增加 120 萬美元」）。
- **最容易寫壞的地方**：使用概念 Mockup 代替真實介面截圖；未展示 2–3 個替代方案的權衡取捨（Trade-offs）；模糊個人真實職責。

### 6. 個股研究報告 (equity-report)

- **讀者決定**：提供超越市場共識的差異化觀點（Variant Perception），評估目標公司之估值、催化劑與下行風險，支援投資決策。
- **篇幅目標**：繁體中文 **2,000–4,500 字**。
- **開頭與結尾規則**：
  - 開頭：首頁第一屏（Above the Fold）直接給出評級、目標價、投資邏輯主張（Thesis）與 3–5 個關鍵驅動因素。
  - 結尾：提供量化風險因素與敏感度分析表，不得僅寫定性免責聲明。
- **最容易寫壞的地方**：使用「營運穩健」等缺乏差異化的套話；僅依賴單一估值模型；未區分 GAAP 與 Non-GAAP 或忽略一次性損益。

### 7. 簡報投影片 (slides)

- **讀者決定**：在簡報過程中，引導聽眾以最快速度抓取每頁核心主張與關鍵證明，建立連貫說服邏輯。
- **篇幅目標**：繁體中文每頁 **40–80 字**（總字數約 **1,200–2,500 字**）。標題另計，上限 110 字元；支撐要點 3–5 項，每項須能單行展示。
- **開頭與結尾規則**：
  - 開頭：封面頁點明主題；每頁標題必須是完整陳述句主張（Declarative Claim），副標（Eyebrow）僅作跨頁分區標籤。
  - 結尾：結尾頁給出單一明確的行動請求（Ask），禁止以「總結清單」收尾。
- **最容易寫壞的地方**：標題僅作主題標籤（如「第三季財報」）；單頁正文 > 80 字或清單 > 5 項；超過 12 頁簡報連續 5 頁以上缺乏章節分隔頁（Chapter Slide）。

### 8. 產品落地頁 (landing-page)

- **讀者決定**：在 3–5 秒內轉化訪客理解產品類別、核心價值與信任證明，完成購買或試用決策。
- **篇幅目標**：繁體中文全頁 **1,000–2,000 字**（包含 Hero、Gallery、Features、Principles、Pricing、FAQ 六大區塊）。
- **開頭與結尾規則**：
  - 開頭：Hero 首屏點明真實產品類別與單句定位標語（無逗號），按鈕僅有試用（Secondary）與購買（Primary）一對。
  - 結尾：FAQ 第一題必須為定位比較問題（如「這與 {{COMMON_TOOL}} 有何不同？」），頁尾以品牌標記與詩意結語收尾。
- **最容易寫壞的地方**：價格數字全頁出現 > 2 次；按鈕文字寫入價格（如 `以 $19 購買`）；FAQ 回答 > 3 句；與 `llms-full.txt` 內容不同步。

## 各類型的品質門檻

本節提供每種類型 5–8 條 Pass/Fail 可判定門檻。檢驗者無需參與寫作即可透過閱讀稿件明確回答「有」或「沒有」。

### 1. 單頁摘要 (one-pager) 品質門檻

1. 全篇繁體中文正文字元數在 400–600 字之間，且在 1280×800 視窗內一屏可讀完，不需捲動。
2. 數據指標卡片（Metrics Cards）數量恰好為 3–4 張，且數據相關內容占正文總篇幅 30% 以上。
3. 每個章節小標題皆為完整陳述句（主張+數據），而非單純主題標籤（例如寫「營收成長 34% 達 1,200 萬美元」，而非「營收狀況」）。
4. 第一段正文首句直接切入核心主張或數據，完全不包含「在當今瞬息萬變……」、「隨著技術發展……」等開場廢話。
5. 必須包含產品/公司 Logo、產品實拍照或 UI 介面截圖中的至少一類；若缺乏素材，版面上必須有明確的「素材缺口標示」。
6. 頁尾必須包含單一明確的下一步行動請求（Ask）與聯絡方式欄位。

### 2. 長篇報告與企劃提案 (long-doc) 品質門檻

1. 包含獨立的「執行摘要」（Executive Summary）頁面，字數在 300–500 字內，並精確列出 3–5 個核心結論要點。
2. 每個章節（h2）開頭第一段必須為 2–3 句的「主張段落」（Claim Paragraph），說明該章節的核心論點與意義。
3. 正文每連續 3–4 個段落（或段落超過 5 行）後，必須穿插提示框（Callout）、引用區（Quote）或圖表/圖片中的至少一種元素。
4. 正文中的所有外部事實數據皆保留來源標記（如「(Gartner, 2026)」或「據 10-K 財報」），可明確區分事實、判斷與推論。
5. 若為企劃提案（Proposal）變體且採用注意力框架，內文禁止出現 `每月 N 篇`、`20 節課程` 或 `全程參與` 等外包工時型明細，改以里程碑與方向標註。
6. 若為無價版本的企劃提案，合作章節名稱必須精確為「合作方向與價值」，且不得出現大字級價格數字。
7. 包含 12 個月以上時程的提案，必須在時程表格之前獨立提供「前 60 天啟動期敘述段落」，說明時間緊迫性與逐月具體動作。
8. 繁體中文總字數在 2,000–6,000 字之間，正文段落間距符合規範，且頁面底端不留空白廢頁。

### 3. 商務書信 (letter) 品質門檻

1. 第一段必須在單一句子內明確說明寫信目的與核心訴求。
2. 結尾段落必須明確寫出具體的請求（Ask）或下一步約定時程。
3. 正文包含 3–5 個中間段落，每個段落僅探討單一論點並附帶對應證據。
4. 全篇完全不包含卡片框線、漸層背景、膠囊標籤或裝飾性圖示等視覺元件。
5. 結尾署名採用 600 字重襯線體，結尾敬語精確對應情境（如「敬禮」、「順頌商祺」或「Best regards」）。
6. 全篇繁體中文總字數在 300–600 字之間，字體行高在 1.7–1.85，單頁完結不產生第二頁。

### 4. 更新日誌 (changelog) 品質門檻

1. 重大變更（Breaking Changes）必須排在版本最頂端，且每項重大變更皆包含具體的遷移指令或程式碼替換範例。
2. 條目依使用者影響層面（Breaking / Features / Fixes）進行分組，禁止以檔案路徑或內部元件名稱分組。
3. 每個變更項目皆為單一句子，以動詞開頭（如「修正……」、「新增……」、「升級……」），且完全不含內部開發術語。
4. 每個版本包含 4–8 個變更項目；若少於 4 項必須與前一版本併頁呈現。
5. 每個版本區塊皆明確標註版本號碼與發布日期快照（格式如 `v2.4.0 · 2026.04`）。
6. 繁體中文單一版本字數在 400–800 字之間。

### 5. 作品集案例 (portfolio) 品質門檻

1. 每個專案案例開頭第一段必須直接講述「問題與代價」，禁止以專案名稱或個人職位作為開場句。
2. 每個案例必須包含三層成效證明：量化指標（如轉換率 +35%）、定性用戶反饋（引言）與商業脈絡（如增加 120 萬美元 ARR）。
3. 每個案例必須明確寫出 2–3 個替代方案之間的權衡取捨（Trade-offs）與最終選擇理由。
4. 每個專案明確標註個人真實職務與參與範疇（如「獨立設計」、「主導 5 人團隊」或「負責後端 API 整合」）。
5. 視覺呈現優先採用真實發布介面截圖，禁止使用純概念美化 Mockup 填充；缺少截圖時必須有「素材缺口標籤」。
6. 全篇包含 3–5 個深度案例，總篇幅在 1,200–2,500 字之間。

### 6. 個股研究報告 (equity-report) 品質門檻

1. 首頁第一屏（Above the Fold）必須包含評級、目標價、投資邏輯主張（Thesis）與 3–5 個關鍵驅動因素清單。
2. 內文包含至少兩種獨立的估值模型（如 DCF 與可比公司乘數法），並提供敏感度分析區間。
3. 所有催化劑（Catalysts）皆標明預期發生時間點（年份與季度）與對財務模型影響的具體數量級。
4. 競爭格局分析必須提供具體市占率數據與成本優勢百分比，不得僅作定性描述。
5. 財務數據分析中，GAAP 與 Non-GAAP 指標明確分列，並標明一次性損益項目。
6. 繁體中文總字數在 2,000–4,500 字之間，且包含至少一項量化的下行風險因素及其對目標價的折讓幅度。

### 7. 簡報投影片 (slides) 品質門檻

1. 每張內容投影片標題必須是完整的陳述句主張（Declarative Claim），禁止僅使用主題標籤（如「第三季營收成長 23%」而非「第三季財報」）。
2. 每張投影片內文字數嚴格限制在 40 個字元以內，且單一清單項目不超過 5 項。
3. 副標（Eyebrow）為跨頁分區標籤，標題為頁面獨特主張，兩者文案不得重疊或同義重述。
4. 每張內容投影片包含「1 項主張 + 3–5 個支撐項目」或「1 張圖表 + 2–3 個重點標註」；少於 3 項且無圖表者必須與相鄰頁合併。
5. 簡報總頁數 ≥ 12 頁時，每 4–6 頁必須穿插一張滿版全黑/深色章節分隔頁（Chapter Slide），且連續內容頁不超過 5 頁。
6. 結尾頁必須為單一明確的行動請求（Ask），不得為「重點複習」清單。
7. 圖說（Caption）必須回答「為什麼這張投影片重要」，提供取捨或洞察，禁止同義重述標題或流程圖。

### 8. 產品落地頁 (landing-page) 品質門檻

1. Hero 首屏第一視角必須明確寫出產品的真實類別名稱與單句定位標語（無逗號）。
2. Hero 區域的按鈕恰好為 2 個：次要試用按鈕（Ghost button）與主要購買按鈕（Filled button）。
3. 價格數字在整頁中出現次數不得超過 2 次（Pricing 區塊一次，Hero Token 一次）。
4. 所有 CTA 按鈕文字僅包含行動指令（如 `購買 {{PRODUCT}}` 或 `免費試用`），禁止將價格寫入按鈕（如 `以 $19 購買`）。
5. Section Lede（區塊前導句）為單一平實句子，不加粗、不套用強調色，且不含競爭對手名稱。
6. FAQ 的第一題必須為定位比較問題（如「這與 {{COMMON_TOOL}} 有何不同？」），且所有 FAQ 回答限制在 1–2 句內。
7. 展覽區（Gallery）提供 3–6 個真實產品介面截圖或終端機工作流面板，且圖說採詩意/具體風格而非行銷用語。
8. 落地頁 FAQ 內容必須與 `landing-page-llms-full.txt.example` 中的問答與定位完全同步。

## 版面 × 內容的耦合規則

內容決策直接影響視覺排印與版面空間。本節定義內容與版面的相互耦合規則，所有排印與色彩限制皆以 `references/design.md` 與 `references/anti-patterns.md` 的規範為基準。

### 1. 強調節奏與數量預算

- **段落強調上限**：單一段落或單行內，文字強調項目**至多 1–2 處**。
- **強調對象限制**：強調僅能施加於**具體量化數據**（如 `34%`）或**獨特短語**，嚴禁強調品質形容詞（如「顯著成長」）。
- **長篇正文頻率**：長篇正文中，每 80–150 字出現 1 處強調為健康頻率；短段落不強行加掛強調。
- **視覺呈現**：行內強調僅能使用橘棕色 `--color-text-accent` 換色或細下劃線，`<strong>` 在正文中應極為罕見。

### 2. 數字格式與 tabular-nums 耦合

- **千分位逗號**：四位數以上數字必須加上半形千分位逗號（如 `5,000+`），禁止寫成 `5000+` 或全形逗號 `5，000+`。
- **百分比格式**：百分比數字與 `%` 之間不得留空格（寫 `90%`，非 `90 %`）。
- **數量級估算**：採用估算值（如 `~$10M`），避免無權威來源的假精確度（如 `$9,876,543`）。
- **日期快照**：版面緊湊欄位或標籤中，日期統一採用 `2026.04` 格式，避免 `2026年4月` 擠壓空間。
- **符號與箭頭**：指示箭頭一律採用標準 Unicode 箭頭 `→`，禁止使用 ASCII 拼寫 `->`。
- **`tabular-nums` 對齊**：所有承載數據、表格與計數數字的 HTML 節點，必須加上 CSS `font-variant-numeric: tabular-nums lining-nums`，避免字寬跳動與舊式數字（oldstyle nums）基線跳動。

### 3. 中英混排與標點符號

- **中文引號**：繁體中文正文引言與強調，一律採用角括號 `「」` 與 `『』`，禁止使用英文直式雙引號 `""`。
- **中英半形空格**：繁體中文正文與拉丁產品名、英文術語或數字之間，必須加上一個半形空格（如：`Next.js 15 框架`、`成長 34% 達 1,200 萬`）。
- **半形標點**：在數據、百分比與日期密集區域，逗號、句點、百分號與號點保持半形。
- **短文案句號與分號禁用**：UI 提示、落地頁特色清單、更新日誌條目等短文案，子句間以逗號連接，句點僅出現於條目末尾或完全省略。**嚴禁在短文案中使用分號 `；` 或條目中段使用句點 `。`**。
- **中英雙層標題比列**：主導覽與章節標題採用「中文主標 + 英文副標」結構。中文主標走 `--serif`，英文副標走 `--sans` 11px 大寫 `.28em` 字距；字級比維持約 **3:1**（如 30px / 11px），英文副標不得與中文主標等比重複。

### 4. 強調不等於加粗與小字限制

- **禁止合成假粗體**：字型僅提供 400（常規）與 600（半粗）字重。600 給標題、強調詞與按鈕，正文一律 400。禁止使用 `font-weight: bold` 合成假粗體。
- **換色不加粗**：行內強調僅套用 `--color-text-accent` 或細下劃線，不得同時疊加 `font-weight: 600` 或 `<strong>`。
- **小字對比度與橘棕色限制**：
  - 橘棕色 `--color-text-accent` 在基底上的對比度僅 3.98:1（漏光區 2.85:1），低於 WCAG 正文 4.5:1 之標準。
  - **在小於 24px 的文字或小字正文中，禁止直接套用 `--color-text-accent` 作為文字顏色**。小字強調必須改用米白正文色 `--color-text-on-dark` 並搭配橘棕底線或符號。

### 5. 正文行寬與圖文容器耦合

- **正文欄寬天花板**：中文正文行寬嚴格限制為 `max-width: 38em`（約 28–42 個繁體中文字），拉丁正文限制 `max-width: 60ch`。中文正文**不得橫跨整個寬螢幕**。
- **圖文結構分離**：圖像承擔敘事，文字承擔結構。**禁止使用卡片容器將圖片與一段文字強行打包在一起**。區域靠非對稱分欄（如 1.618:1、7:5、8:4）與負空間區隔，讓圖與文在版面上升降與嵌合。

### 6. 頁型分級與正文欄置中耦合

- **A 級頁面（敘事型）**：適用於 `portfolio`、`slides`、`landing-page`。允許較高漏光強度與最多 3 種裝飾語彙。
- **C 級頁面（閱讀型）**：適用於 `one-pager`、`long-doc`、`letter`、`changelog`、`equity-report`。漏光 alpha 必須降低至 0.10 / 0.08。
- **正文欄置中收窄**：C 級頁面的正文欄**必須置中收窄**，寬度不得超過 `--measure`（38em）。不能僅靠全域容器上限（1200px），必須確保正文欄位覆蓋的背景 luma 最大值 ≤ 20 且欄內極差 ≤ 8，以防止邊緣正文落入漏光亮區破壞對比。

## 顯影模式

**罕用。** 使用者沒有明確指定就不要用。以下規格只在他指定時才生效。

### 這個模式在做什麼

把主觀意識與品牌主張降維映射，凝固為具備物理刻度、幾何光影與磨損痕跡的客觀實體紀錄。

```
[主觀意圖 / 抽象宣示] ──► [物理對應轉譯] ──► [冷澈實體紀錄]
```

傳統文案靠主觀情緒與抽象形容詞宣示價值。這個模式剔除心理描寫，改用客觀觀察者視角：看不見的精神意圖，必須轉換成可觀察的自然現象、機械運轉或空間數據。

它調整的是**語域與選詞**，不是資訊密度，也不是修辭密度。設計語言有一條原則直接約束它：**圖像承擔敘事與氣氛，文字承擔結構。**氣氛已由顆粒、漏光、襯線字與非對稱分欄承擔，文字再去做同一件事只會兩層打架。

### 三個手段

**詞彙映射。** 用「刻度、頻率、抗力、邊界、光影、沉澱」覆蓋「品質、創新、熱情、完美」這類感性形容詞。

**句法控制。** 採「名詞／動詞 + 介詞短語 + 物理結果」的客觀陳述句。

**鏡頭定格。** 段落交接處可插入無生命物體的靜態陳述（儀器聲響、材料磨損、光線偏移）作為留白。定格句自成一段、每份文件至多兩處，且**不得取代任何一段的主張句**。

### 地板：可以不用數字，但必須指得出東西

這個模式唯一的失敗形態是**物理外衣的空話**。刻度、抗力、頻率這類詞會讓空洞的句子讀起來像實證 —— `anti-patterns.md`〈內容空洞〉抓得到「顯著成長」，抓不到「材料物理抗力」。

所以：**物理對應必須指向該文件裡真實存在的物件、約束或數據。不得引入題材中不存在的物理。**

| | 例 | 判定 |
|---|---|---|
| ✓ | 第二階段：實驗數據採集，與邊界條件的再次覆核 | 指得出對象，可查證 |
| ✗ | 於混亂的頻率之中，標定一處明確的經緯與刻度 | 說有明確經緯卻不給經緯 —— 「探索無限可能」換了一套儀器外衣 |
| ✗ | 齒輪咬合精度與材料物理抗力，決定物件在歲月中的運轉軌跡 | 產品若不是機械，齒輪是**虛構的物理**。比抽象形容詞更糟，因為它看起來像事實 |

品質門檻、內容契約與反模式全部照舊。**每一段仍然要能回答「所以呢」。**

### 禁區

- **不寫年代戲仿。** 不用民國紀年、不用文言腔、不用「彼時」「猶記」這類仿舊詞。質感來自材質，不來自扮演。
- **不用數位時代的企業套話。** 賦能、打造、閉環、抓手、生態、全鏈路 —— 標準模式已禁，這裡更刺眼，因為它們把畫面拉回會議室。
- **不堆疊形容詞。** 「優雅而克制的、帶著溫度的設計」是三個形容詞在講同一件不存在的事。
- **不用破折號串接情緒**，不用刪節號製造餘韻。標點不是氣氛工具。
- **英文語軌不做時代仿寫。** 同樣走物理對應與客觀視角，但不模仿任何時期的英文文體。

### 兩個模式的同一段話

同一則產品更新，兩種寫法都合格：

> **標準模式**　匯入流程重寫，1 萬列的檔案處理時間從 47 秒降到 6 秒。舊版逐列寫入資料庫，新版改為批次交易。既有匯入設定不受影響。

> **顯影模式**　舊的匯入逐列寫入，一萬列在資料庫前排隊 47 秒。改為批次交易後，同一份檔案落地耗時 6 秒。既有設定不受影響。

兩段給的是同一組事實與同一個數字。差別在觀察的位置 —— 後者把「流程」換成看得見的動作與耗時。若顯影版少了數字或多了形容詞，那就不是切換模式，是寫壞了。

## 圖解判斷

本專案**不附圖解資產庫**，也沒有圖表轉換管線。圖解要嘛是外部產生的影像放進 `.plate` 圖版，要嘛是手寫的行內 SVG。因此「該不該畫」比「用哪個模板畫」重要得多。

### 畫之前先回答這一句

> 一段寫得好的文字，會比這張圖教給讀者的更少嗎？

答案是「不會」就別畫。圖解替文字加值的地方只有三種：**層級、方向、量級**。這三樣文字表達起來費力，圖表表達起來省力。除此之外的圖都是裝飾。

### 該畫什麼

| 要表達的 | 用 |
|---|---|
| 系統元件與連線 | 架構圖 |
| 決策分支（若 A 則 B 否則 C） | 流程圖 |
| 兩軸定位、優先排序 | 象限圖 |
| 類別比較（營收、市佔、分季） | 長條圖 |
| 隨時間的趨勢 | 折線圖 |
| 組成佔比 | 環圈圖 |
| 有限狀態與轉移 | 狀態機 |
| 時間軸與里程碑 | 時間軸 |

不在表上的兩種：

- **比較兩個東西** —— 用表格。三欄表格勝過任何二元對比的圖。
- **一個方框加一個標籤** —— 刪掉方框，把那句話寫出來。

### 複雜度預算

編輯型文件（報告、單頁方案、簡報）的目標密度是 **4/10**：技術上完整，但讀者不需要一本說明書才看得懂。

- 節點超過 9 個 → 這是兩張圖，不是一張
- 兩個節點永遠一起出現 → 它們是同一個節點
- 一條線的意思從版面就看得出來 → 刪掉那條線
- 五個元素同時用強調色 → 你還沒決定焦點是什麼

**焦點規則**：每張圖 1–2 個焦點元素，其餘一律中性色。焦點來自對比，不是來自數量。

技術教學型文章的密度可以到 **6–7/10**（讀者是來學運作原理的），需要帶上分層、資料流方向，以及至少一個標示出來的取捨點。在那種脈絡下交出三個方框的「架構圖」，讀者會直接說那是行銷圖。

### 圖說寫判斷

圖說寫**判斷**而非資料範圍。

- ✗ 2023–2025 年營收數據
- ✓ 營收在 Q3 轉正，第二季的價格調整是轉折點

標題同理。「各季度營收」是標籤，「第二季價格調整後營收加速成長」才是標題。

圖說也不寫觀點歸屬（「筆者認為」「我們觀察到」）—— 圖說的位置本身就代表這是作者的判斷。

### 版面約束

- 圖版走 `.plate`，圖說用 `<figcaption>`，編號用 `.plate-num`（等寬字，如 `FIG. 04`）。
- 影像一律要有 `alt`。純裝飾的遮罩層 `.plate-mask` 要帶 `aria-hidden="true"`。
- 寬圖表必須外包 `overflow-x: auto` 容器，不得讓整頁出現水平捲軸。
- 圖表的色彩只能用既有 token。圖表不是引進第二套色系的藉口。
